## 一、这一部分总讲法

各位老师，接下来介绍本文的第一个主要工作：基于 CUDA 的 OCT 图像实时重建。

前面已经说明，SD-OCT 系统的光谱仪采集到的是原始干涉谱信号，而不是可以直接用于语义分割的 OCT 图像。因此，在后续模型提取匙孔区域之前，需要先完成一整套 OCT 后处理重建流程。本文第三章主要解决的就是这个重建流程的实时性问题。

具体来说，一帧 B-scan 可以看作一个 `M × N` 的原始光谱矩阵。其中，`M` 表示这一帧中包含多少条 A-scan，`N` 表示每条 A-scan 的光谱采样点数，本文中 `N = 2048`。每一条 A-scan 经过 K 线性化、FFT 和幅值映射之后，得到一条深度方向的反射信号；多条 A-scan 按照横向扫描顺序排列，就形成二维 OCT B-scan 深度图像。

传统 CPU 处理在 K 线性化和 FFT 等步骤上耗时较高，难以匹配 82 kHz 的 A-scan 采集速率。因此本文将 SD-OCT 后处理流程整体迁移到 GPU 端，并重点优化 K 线性化中的三对角方程组求解和 CPU-GPU 数据传输开销。

这一章的主要工作可以概括为三点：

1. 将完整 SD-OCT 后处理链路组织成 CUDA 流水线；
2. 将 K 线性化中的 Thomas 串行三对角求解改为 PCR 并行求解；
3. 结合共享内存、常量内存、只读缓存、统一内存和事件同步，优化访存和小 B-scan 低延迟处理。

## 二、第 8 页：PART 02 OCT 图像实时重建

### 讲稿

这一部分介绍本文的第一个核心工作：OCT 图像实时重建。

在 SD-OCT 系统中，传感器直接采集到的是光谱干涉信号，而不是深度图像。也就是说，后续语义分割模型不能直接使用原始光谱数据，必须先通过后处理将光谱信息转换为深度方向的信息。

本文的 OCT 后处理主要包括类型转换、光谱整形、背景扣除、K 线性化、色差补偿、FFT、幅值提取和帧合并等步骤。其中，K 线性化和 FFT 是计算量较大的环节，也是影响在线处理速度的主要瓶颈。

因此，本章的目标是将上述后处理流程迁移到 GPU 端，通过 CUDA 并行计算提高重建速度，使重建链路能够满足激光焊接在线监测的实时性要求。

### 过渡句

下面先看 SD-OCT 后处理流程中，具体哪些步骤会成为计算瓶颈，以及本文是如何设计 CUDA 流水线的。

## 三、第 9 页：CUDA PIPELINE

### 页面重点

这页要讲清楚：

- SD-OCT 后处理有 8 步；
- 慢的核心是 K 线性化和 FFT；
- 本文不是只加速某一个函数，而是把整条链路放到 GPU；
- 数据尽量单次输入、设备端处理、单次输出。

### 讲稿

这一页展示的是 SD-OCT 后处理流程中的主要瓶颈和 CUDA 优化思路。

首先，从输入来看，光谱仪采集到的是 `M × N` 的原始干涉谱矩阵。`M` 是一帧 B-scan 中 A-scan 的数量，`N = 2048` 是每条 A-scan 的采样点数。这个原始矩阵不能直接作为图像使用，需要经过一系列后处理才能得到 OCT 深度图。

本文的完整后处理流程包括 8 个步骤：第一步是把采集卡输出的 `uint16` 数据转换为 `float`；第二步是光谱整形，也就是对光源光谱包络进行归一化；第三步是背景扣除，用于去掉直流背景和固定偏移；第四步是 K 线性化，把非均匀的 k 空间采样重采样到均匀 k 网格；第五步是色差补偿；第六步是 FFT，将 k 域信号变换到深度域；第七步是幅值提取和灰度映射；最后一步是帧合并，用于降低随机噪声。

在这些步骤中，计算瓶颈主要集中在 K 线性化和 FFT。K 线性化需要对每条 A-scan 做三次样条插值，其中三次样条插值又涉及三对角方程组求解；FFT 则需要对每条 A-scan 进行 2048 点频域变换。如果这些步骤在 CPU 上逐条 A-scan 串行处理，就很难满足 82 kHz 的采集速率。

因此，本文的第一层优化是流程级优化：将整条后处理链路迁移到 GPU 端。对于类型转换、光谱整形、背景扣除、色差补偿和幅值映射这类逐点运算，每个线程负责一个或多个采样点；对于 FFT，调用 cuFFT 对多条 A-scan 批量处理；对于最难并行的 K 线性化，则单独设计 PCR 并行求解核函数。

从数据流角度看，本文尽量让数据在 GPU 端驻留。原始干涉谱输入后，中间结果都在设备端缓冲区之间传递，只在最后输出重建结果时返回主机端。这样可以减少 CPU 和 GPU 之间反复拷贝带来的传输开销。

### 这页一句话总结

> 本文不是单独加速某一步，而是把原始干涉谱到 OCT 深度图的完整后处理流程设计成 GPU 端流水线。

## 四、第 10 页：数据留在 GPU，PCR 求解

### 页面重点

这页是第三章的核心实现图，要讲：

- Host 端负责采集和调度；
- GPU 端执行后处理流水线；
- 统一内存减少显式拷贝；
- PCR 负责 K 线性化中的三对角求解；
- 共享内存、常量内存、只读缓存优化访存。

### 讲稿

这一页展示的是本文 CUDA 重建流水线的具体执行过程。

左侧是 Host 端，也就是 CPU 端。CPU 主要负责从采集卡接收原始干涉谱数据、准备输入缓冲区，并按顺序启动 GPU 上的 kernel。真正的大规模计算在 GPU 端完成。

进入 GPU 之后，数据首先完成类型转换，将采集卡输出的 16 位无符号整数转换为 32 位浮点数。随后进行光谱整形和背景扣除，去除光源包络不均匀和直流背景的影响。之后进入最关键的 K 线性化步骤，本文在这里使用 PCR 并行求解三对角方程组。K 线性化完成之后，再进行色差补偿、cuFFT 频域变换和幅值映射，最终输出 OCT B-scan 深度图。

这里有三个关键优化点。

第一个是数据驻留。传统做法中，CPU 和 GPU 之间可能存在多次 Host-to-Device 和 Device-to-Host 拷贝。本文尽量让数据在 GPU 端连续流动，中间步骤不再回传 CPU，从而减少 PCIe 传输和同步开销。

第二个是 PCR 并行求解。K 线性化采用三次样条插值，需要先求解一个 2048 阶三对角方程组。传统 Thomas 算法存在前后依赖，不适合 GPU 并行。本文将其改为 PCR，并行循环规约算法。对于 `N = 2048`，PCR 只需要 `log2(2048) = 11` 层迭代，每一层内多个采样点可以由 block 内线程并行更新。

第三个是 CUDA 存储层次优化。PCR 中的三对角系数 `a、b、c、d` 和二阶导数 `y2` 会被频繁读写，因此放入共享内存；插值节点 `Lambda1` 等固定参数放入常量内存；原始信号读取使用只读缓存路径。这样可以减少对全局内存的访问，提高 K 线性化阶段的执行效率。

因此，这页的重点是说明：本文将重建流程组织为 GPU 端流水线，并针对最耗时的 K 线性化步骤进行了算法和内存两方面优化。

### 可补充底层解释

代码中 PCR kernel 的调用形式是：

```cpp
size_t shmem_bytes = 6 * LENGTH * sizeof(float);
dim3 grid(M), block(256);
splineInterpKernelV2_optimized_PCR<<<grid, block, shmem_bytes>>>(...);
```

它的含义是：

- `grid(M)`：一条 A-scan 对应一个 CUDA block；
- `block(256)`：每个 block 内 256 个线程；
- `shmem_bytes`：为每个 block 分配动态共享内存；
- `6 * LENGTH`：共享内存中存 6 个长度为 2048 的数组。

## 五、第 11 页：GPU/CUDA 计算框架

### 页面重点

这页用于向老师解释 CUDA 的底层执行模型。

### 讲稿

这一页主要说明本文 CUDA 实现所依赖的计算框架。

在 CUDA 中，CPU 端称为 Host，GPU 端称为 Device。Host 主要负责控制流程、准备数据和启动 kernel；Device 负责执行大规模并行计算。

GPU 端的线程组织分为三个层次：Grid、Block 和 Thread。一个 Grid 由多个 Block 组成，一个 Block 中包含多个 Thread。Thread 是最基本的执行单位，多个 Thread 会组成 Warp 进行调度，一个 Warp 通常包含 32 个线程。

对应到本文的 OCT 重建任务中，一帧 B-scan 是由多条 A-scan 组成的，而不同 A-scan 之间大部分计算是相互独立的。因此，可以将不同 A-scan 分配给不同 block。同时，每条 A-scan 内部有 2048 个采样点，这些采样点上的类型转换、插值、乘法和幅值计算又可以进一步分配给 block 内的多个线程。

举例来说，类型转换 kernel 中，每个线程只负责一个采样点：

```cpp
int idx = blockIdx.x * blockDim.x + threadIdx.x;
if (idx < total)
    dvc_img[idx] = (float)dvc_img1[idx];
```

这里 `idx` 是全局线程索引，对应 `M × N` 原始矩阵中的一个元素。这个线程只需要把该元素从 `uint16` 转换为 `float`。这种逐点独立操作非常适合 GPU 并行。

对于 K 线性化，情况更复杂，因为三次样条插值需要求解三对角方程组。本文采用的映射方式是：每个 block 处理一条 A-scan，block 内 256 个线程协同完成 PCR 迭代。这样既保留了 A-scan 之间的并行，又利用了 A-scan 内部采样点之间的并行。

所以，这页的核心含义是：CPU 管流程，GPU 做批量计算；本文根据 OCT 数据结构，将 A-scan、采样点和 FFT 批处理映射到 CUDA 的 Grid、Block 和 Thread 层次中。

### 这页一句话总结

> 本文的并行化不是简单开很多线程，而是把 OCT 数据结构映射到 CUDA 的线程层次：B-scan 对应 grid，A-scan 对应 block，采样点对应 thread。

## 六、第 12 页：PCR K 线性化

### 页面重点

这是第三章最重要的算法页。必须讲清：

- 为什么需要 K 线性化；
- 为什么三次样条需要三对角求解；
- Thomas 为什么不适合 GPU；
- PCR 为什么适合 GPU；
- PCR 不是自己发明的，但 CUDA 实现和应用是本文工作。

### 讲稿

这一页重点介绍 K 线性化中的 PCR 并行求解。

首先解释为什么需要 K 线性化。OCT 深度重建依赖傅里叶变换，而 FFT 要求输入信号在波数 k 空间上均匀采样。但光谱仪采集到的数据通常是按照像素或波长分布的，转换到 k 空间后并不是严格等间隔。如果直接做 FFT，重建后的深度峰会展宽，轴向分辨率下降，进而影响后续匙孔边界和熔深估计。因此，需要将原始采样点重新插值到均匀 k 网格上，这一步就是 K 线性化。

本文采用三次样条插值进行 K 线性化。相比线性插值，三次样条具有更好的平滑性和插值精度，但它需要先求解每个节点处的二阶导数。这个过程会形成一个三对角线性方程组：

```text
a[i] * y2[i-1] + b[i] * y2[i] + c[i] * y2[i+1] = d[i]
```

传统方法通常使用 Thomas 算法，也就是追赶法。Thomas 算法在 CPU 上很高效，但它存在明显的前后依赖：前向消元时第 `i` 行依赖第 `i-1` 行，回代时又依赖后一个结果。因此，在 GPU 上如果仍然使用 Thomas 算法，就会出现一个线程串行求解，而同一 block 中其他线程等待的情况，不能充分利用 GPU 并行能力。

为了解决这个问题，本文引入 PCR，也就是 Parallel Cyclic Reduction，并行循环规约算法。PCR 的基本思想是分层消去相邻变量之间的依赖。第 0 层消去相邻 `±1` 的依赖，第 1 层消去 `±2` 的依赖，第 2 层消去 `±4` 的依赖，以此类推。对于本文的 `N = 2048`，需要 `log2(2048) = 11` 层迭代。

在每一层迭代中，不同行的系数更新可以由多个线程同时完成。因此，PCR 更适合 GPU 的并行执行模式。本文实现中，每个 CUDA block 处理一条 A-scan，block 内 256 个线程协同维护三对角系数 `a、b、c、d`，并在共享内存中完成 11 层 PCR 迭代。迭代结束后，每一行方程都近似变成独立形式，线程只需要执行一次除法即可得到二阶导数 `y2`。

从实验精度看，PCR 与 MATLAB spline 的误差保持在较小范围内，RMSE 为 `1.2e-5`，说明 PCR 在保持三次样条插值精度的同时，提高了并行求解效率。

所以，这页的结论是：PCR 算法本身是成熟的并行三对角求解方法，本文的工作是将它应用到 OCT K 线性化的三次样条求解中，并结合 CUDA 线程映射和共享内存实现，解决 Thomas 算法在 GPU 上并行度不足的问题。

### 这页一句话总结

> Thomas 适合 CPU 串行，PCR 适合 GPU 并行；本文用 PCR 把 K 线性化中的三对角求解从串行依赖改成 11 层并行迭代。

## 七、第 13 页：重建速度结果

### 页面重点

这页要证明“确实快，而且超过采集需求”。

### 讲稿

这一页展示的是不同平台下 OCT 重建速度的对比。

在 `M = 1000, N = 2048` 的测试条件下，CPU MATLAB 实现的处理速率约为 `11.6k A-line/s`，CPU C++ 实现约为 `19k A-line/s`，而本文基于 RTX 4090D 的 CUDA 实现达到了 `1351k A-line/s`。

从单帧耗时来看，CUDA 重建一帧 B-scan 约为 `0.74 ms`。与 MATLAB 实现相比，速度提升约 `117` 倍；与 C++ 实现相比，速度提升约 `71` 倍。

这里需要和采集速率进行比较。本文系统的 A-scan 采集速率是 `82 kHz`，也就是每秒约 82000 条 A-scan。而 CUDA 重建速率达到 `1351k A-line/s`，明显高于采集需求。这说明从吞吐量角度看，本文的 GPU 重建链路已经能够满足在线处理要求。

不过，这里也需要说明一点：吞吐量足够并不意味着闭环控制中所有延迟问题都解决了。对于实际在线焊接控制，还需要考虑小 B-scan 批量、采集同步、模型推理和控制输出等因素。因此下一页进一步分析不同 B-scan 粒度下的延迟表现。

### 这页一句话总结

> CUDA 重建速率达到 1351k A-line/s，已经超过 82 kHz 的采集速率要求，说明重建吞吐量满足在线处理需求。

## 八、第 14 页：Small B-scan / 统一内存优化

### 页面重点

这页要讲“为什么 M 越小，统一内存越有价值”。

### 讲稿

这一页进一步分析小 B-scan 场景下的端到端延迟。

前面一页主要关注的是大批量情况下的整体吞吐量。但在焊接在线监测或闭环控制中，系统不一定总是等待很大的 B-scan 批量再处理。为了降低反馈延迟，可能希望以更小的 `M` 进行高频处理。例如 `M=50` 或 `M=100` 时，单次计算量会明显下降。

但是，当 `M` 变小时，计算量虽然减少，CPU-GPU 之间的数据拷贝和同步这类固定开销并不会等比例减少。也就是说，小 B-scan 场景下，系统可能从计算受限变成传输和同步开销受限。

因此，本文引入统一内存和事件同步进行优化。统一内存允许 CPU 和 GPU 通过同一个指针访问输入输出缓冲区，减少显式 `cudaMemcpy` 管理；事件同步则可以替代部分全局同步，避免 CPU 在不必要的位置被完全阻塞。

从结果可以看到，当 `M = 1000` 时，传统方案从 `742 us` 降到 `685 us`，加速比为 `1.08`，提升不算特别大，因为这时计算量占主导。但当 `M = 50` 时，传统方案耗时 `289 us`，统一内存方案降低到 `178 us`，加速比达到 `1.62`。这说明统一内存和事件同步对小批量低延迟场景更有价值。

因此，这一页说明本文不仅关注大批量吞吐量，也关注在线控制中更实际的小 B-scan 低延迟处理能力。

### 这页一句话总结

> 统一内存不是所有情况下都一定更快，它主要改善的是小 B-scan 下固定拷贝和同步开销占比过高的问题。

## 九、第三章总结稿

第三章主要围绕 OCT 图像实时重建展开，目标是将原始干涉谱快速重建成可用于后续分割的 OCT 深度图像。

本文首先将 SD-OCT 后处理流程完整迁移到 GPU 端，构建了从类型转换、光谱整形、背景扣除、K 线性化、色差补偿、FFT 到幅值映射的 CUDA 流水线。对于逐点计算步骤，采用线程级并行；对于 FFT，使用 cuFFT 批量处理多条 A-scan。

其次，针对 K 线性化中的三次样条插值瓶颈，本文将传统 Thomas 串行三对角求解改为 PCR 并行求解。PCR 通过 11 层并行迭代消除串行依赖，每个 CUDA block 处理一条 A-scan，block 内 256 个线程协同求解三对角系数，从而提高 GPU 线程利用率。

最后，本文结合 CUDA 存储层次进行优化，将三对角系数和二阶导数放入共享内存，将固定插值节点放入常量内存，原始信号读取走只读缓存；同时针对小 B-scan 场景，引入统一内存和事件同步，减少显式数据拷贝和全局同步开销。

实验结果表明，在 `M=1000, N=2048` 条件下，本文 CUDA 重建单帧耗时约 `0.74 ms`，处理速率达到 `1351k A-line/s`，相对 MATLAB 加速约 `117` 倍，相对 C++ 加速约 `71` 倍，已经高于 `82 kHz` 的 A-scan 采集需求。因此，第三章为后续语义分割和在线熔深估计提供了实时 OCT 图像输入。

# Q&A

## Q1：PCR 是调库还是自己写的？

不是调库。PCR 三对角求解是在本文 CUDA kernel 中自己实现的。

答辩回答：

> PCR 不是调用现成库，而是在 CUDA kernel 中自行实现的并行循环规约算法。具体实现中，每个 block 处理一条 A-scan，block 内 256 个线程共同维护三对角系数，并完成 11 层 PCR 迭代。FFT 阶段调用的是 cuFFT 库，但 K 线性化中的 PCR 求解是本文自己实现的。

## Q2：共享内存是自己实现的吗？

共享内存是 CUDA 提供的硬件存储空间，但申请、划分和使用方式是程序员自己写的。

答辩回答：

> 共享内存是 CUDA 的硬件特性，但本文在 kernel 中显式申请动态共享内存，并手动划分为 `sLambda1、s_a、s_b、s_c、s_d、s_y2` 六段，用于缓存插值节点、三对角系数和二阶导数。这部分不是库自动完成的，而是根据 PCR 的访问模式进行的手动设计。

## Q3：PCR 算法成熟吗？算不算创新？

PCR 是成熟算法，本身不是本文原创。

答辩回答：

> PCR 是成熟的并行三对角方程组求解算法，本文不把 PCR 算法本身作为理论创新。本文的创新主要体现在将 PCR 引入到 SD-OCT K 线性化的三次样条插值环节，并结合 OCT 数据结构进行了 CUDA 实现和存储优化。也就是说，创新点在于面向激光焊接 OCT 实时重建任务的算法移植、并行化实现和工程优化。

## Q4：为什么不用 Thomas 算法？

Thomas 适合 CPU 串行，不适合 GPU 并行。

答辩回答：

> Thomas 算法的前向消元和反向回代存在强前后依赖，第 `i` 行计算依赖上一行结果。在 CPU 上这种串行流程是高效的，但在 GPU 上会导致一个线程工作、其他线程等待。本文希望充分利用 GPU 的线程并行能力，因此采用 PCR，将串行依赖转化为 11 层并行迭代。

## Q5：为什么不用线性插值？

线性插值快，但精度和连续性不如三次样条。

答辩回答：

> 线性插值计算简单，容易并行，但它只是一阶分段近似，在节点处导数不连续，可能带来深度峰展宽和重建误差。本文希望保证 K 线性化的精度，因此采用三次样条插值。三次样条带来的三对角求解瓶颈，则通过 PCR 并行化解决。

## Q6：FFT 是自己写的吗？

不是。FFT 调用的是 NVIDIA cuFFT。

答辩回答：

> FFT 阶段本文调用 NVIDIA cuFFT 库完成，因为 cuFFT 已经针对 GPU 做了高度优化。本文的重点不是重新实现 FFT，而是将 cuFFT 融入完整 OCT 重建流水线，并重点优化 K 线性化和数据流组织。

## Q7：为什么 K 线性化必须放在 FFT 前？

因为 FFT 要求输入在 k 空间均匀采样。

答辩回答：

> OCT 深度重建中的傅里叶变换默认输入信号在波数 k 空间等间隔采样。但光谱仪的原始像素到 k 空间的映射通常不是线性的。如果不做 K 线性化，FFT 后的深度峰会展宽，轴向分辨率下降，后续匙孔边界和熔深估计也会受影响。因此 K 线性化必须在 FFT 前完成。

## Q8：统一内存是不是一定比显式 cudaMemcpy 快？

不是。

答辩回答：

> 统一内存并不是在所有场景都更快。对于大批量数据，显式 `cudaMemcpy` 也可以很高效，而且计算时间往往占主导。本文使用统一内存主要是针对小 B-scan 的低延迟场景。当 `M` 较小时，计算量减少，固定数据传输和同步开销占比变高，统一内存和事件同步可以降低这部分开销，因此在 `M=50`、`M=100` 等小批量场景下提升更明显。

## Q9：为什么 M=1000 时提升不明显，M=50 时提升明显？

因为性能瓶颈不同。

答辩回答：

> 当 `M=1000` 时，计算量较大，整体耗时主要由 GPU kernel 和 FFT 计算决定，数据搬运占比相对较低，所以统一内存提升有限。当 `M=50` 时，计算量明显减少，但每次调用仍然存在固定的拷贝和同步开销，这部分占比变高，因此统一内存和事件同步带来的收益更明显。

## Q10：第三章的主要创新点怎么概括？

答辩回答：

> 第三章的主要创新不是提出新的数学理论，而是面向激光焊接 OCT 在线重建场景，完成了后处理链路的 GPU 并行化和工程优化。具体包括：第一，将完整 SD-OCT 后处理流程构建为 CUDA 流水线；第二，将 K 线性化中的 Thomas 串行三对角求解改为 PCR 并行求解；第三，结合共享内存、常量内存、只读缓存、统一内存和事件同步优化访存与低延迟处理。最终实现了 0.74 ms 每帧、1351k A-line/s 的重建速度。

## Q11：如果老师问“这和实时焊接控制有什么关系”？

答辩回答：

> 在线焊接控制需要尽快获得匙孔深度信息。OCT 采集端虽然可以高速获取原始干涉谱，但如果后处理重建速度跟不上，后面的分割和熔深估计就无法实时进行。因此第三章解决的是整条链路中的前端实时输入问题。只有先实时重建出 OCT 图像，后续的语义分割和熔深估计才有在线应用的基础。

## Q12：如果老师问“你这个 0.74 ms 是不是包含全部流程”？

答辩回答：

> 这里的 0.74 ms 是在 `M=1000, N=2048` 条件下，完整 OCT 后处理链路的端到端重建耗时，包括主要 kernel、cuFFT 以及数据传输等流程。具体各核函数耗时在论文第三章中有分解，其中 PCR 样条插值是计算核函数中耗时最高的一项，数据传输也占有一定比例，因此后续又做了统一内存和事件同步优化。

## Q13：如果老师问“为什么每个 block 处理一条 A-scan”？

答辩回答：

> 因为三次样条 K 线性化中的三对角方程组是按每条 A-scan 独立求解的。不同 A-scan 之间没有依赖，因此可以用不同 block 并行处理；而同一条 A-scan 内部有 2048 个采样点，需要 block 内线程协同完成 PCR 求解和插值。这样的映射同时利用了 A-scan 之间的并行和 A-scan 内部的采样点并行。

## Q14：如果老师问“共享内存为什么有用”？

答辩回答：

> PCR 迭代中，三对角系数 `a、b、c、d` 和右端项会被每一层反复读取和写回。如果全部放在全局内存中，每轮迭代都要访问较慢的显存。共享内存位于同一个 block 内，访问延迟更低，适合保存这些高频访问的中间数组。因此本文将 PCR 的核心数据放入共享内存，以减少全局内存访问，提高 K 线性化效率。

## Q15：如果老师问“误差会不会因为 PCR 变大”？

答辩回答：

> 本文将 PCR 结果与 MATLAB spline 结果进行了对比，最大绝对误差为 `3.8e-5`，RMSE 为 `1.2e-5`，与 Thomas 方法处于同一数量级，明显优于线性插值。因此，在本文任务中，PCR 基本保持了三次样条插值的数值精度，同时提高了并行执行效率。

# 最后 30 秒压缩版

> 第三章主要解决 OCT 图像实时重建问题。SD-OCT 采集到的是原始干涉谱，必须经过光谱整形、背景扣除、K 线性化、色差补偿、FFT 和幅值映射才能得到 OCT 深度图。本文将完整后处理流程迁移到 GPU，构建 CUDA 流水线。核心瓶颈是 K 线性化中的三次样条三对角求解，传统 Thomas 算法串行依赖强，不适合 GPU，因此本文采用 PCR 并行循环规约算法，将 2048 阶求解转化为 11 层并行迭代，并结合共享内存、常量内存和只读缓存优化访存。最后通过统一内存和事件同步改善小 B-scan 延迟。实验中 CUDA 重建达到 0.74 ms 每帧、1351k A-line/s，超过 82 kHz 采集需求，为后续分割和熔深估计提供实时输入。
